# AFL Data Foundations

Day 1 data foundations notebook for an AFL match- and player-outcome prediction project. Covers data inventory, target definition, exploratory analysis, leakage-safe feature engineering, and a reproducible train/hold-out split — the contract that Day 2 modeling builds on.

## Source Data

Four raw AFL datasets (not included in this repo — place under `data/` or update the notebook's input path before running):

- `afl_players_info_raw` — one row per player (grain: player-level)
- `afl_players_round_by_round_stats_raw` — one row per player performance per match/round (grain: player × match)
- `afl_players_seasonal_stats_raw` — one row per player per season (grain: player × season)
- `team_matches_home_away_raw` — one row per team's perspective of a match (grain: team × match)

~43 seasons of coverage (1983–2025), 3,100+ player IDs.

## Tasks

**Task 1 — Data Inventory & Understanding.** Loads all four raw datasets, infers grain by testing id-column combinations, documents join keys, and audits missingness, duplicates, and structural/naming inconsistencies across datasets. Key finding: `id` alone is not a reliable player-match key — `player_id + match_date` is used instead — and `match_key` needs additional validation since a number of match keys have only one team row rather than two.

**Task 2 — Prediction Target Definition.** Defines the four modeling targets (see [Target Definitions](#data-dictionary--target-definitions) below) and documents leakage rules: no same-match statistic (disposals, goals, fantasy points) may be used to predict that match's own target. Resolves an initial team-name mismatch via alias mapping to achieve consistent match-key pairing.

**Task 3 — Exploratory Data Analysis.** Examines team win rates, home-ground advantage, season-level trends, and player-level distributions (disposals, goals, fantasy points) and their inter-relationships. A reliable player-position field was not available in the source data, so positional comparisons were excluded rather than inferred.

**Task 4 — Feature Engineering.** Builds 12 leakage-safe features (rolling form, win streaks, head-to-head history, ladder position, rest days — full list in the [data dictionary](#data-dictionary--target-definitions)), each computed only from information available strictly before the match being predicted. Assembles the final per-team-per-match feature table.

**Task 5 — Reproducible Train/Hold-Out Split.** Implements `time_based_split()`, a reusable function that holds out the most recent season chronologically rather than splitting randomly — random splitting would leak future rolling-average information into training. Includes an explicit overlap assertion (no `match_key` appears in both train and hold-out) and applies the identical split to both the team-level and player-level feature tables so every Day 2 model uses the same boundary.

## Known Limitations

- **`match_outcome` framing.** The modeling-decision markdown in Task 2 frames the match target as match-level Home Win / Away Win / Draw. The target actually implemented and carried into `y` is the team-perspective Win/Loss/Draw label; a separate match-level directional version (`determine_match_winner`) is exploratory and not yet wired into the feature/target pipeline. Resolve before Day 2 modeling.
- **No player-position field.** Source data does not reliably support positional splits; Task 3 excludes rather than infers this.
- **Realistic accuracy ceiling.** For match-outcome prediction, expect mid-60s–low-70s% accuracy at best given real-world randomness (injuries, umpiring, weather). Near-95–100% accuracy on any Day 2 model should be treated as a leakage red flag, not a result to trust.
